# OpenSpec 学习与实践指南

## 1. 什么是 OpenSpec？

**OpenSpec** 是一个轻量级的开源框架，专为提升 AI 辅助软件开发（AI Coding）的质量而设计。它推行 **规范驱动开发 (Spec-Driven Development, SDD)** 工作流，旨在确保人类开发者和 AI 编程助手在编写任何代码之前，首先就具体需求和系统设计达成绝对共识。

通过引入机器和人类可读的执行规范，OpenSpec 有效解决了完全依赖 AI 自由挥洒的 “Vibe Coding” 所带来的输出不可预测、难以审查与维护的通病。

---

## 2. 核心理念与架构特征

### 2.1 告别 Vibe Coding，拥抱 SDD

- **传统 AI 编程 (Vibe Coding)**：开发者给出模糊的 Prompt，AI 自由发挥输出。小项目可行，但面对复杂工程时会导致维护性崩塌。
- **规范驱动开发 (SDD)**：通过一份详尽的、版本控制的规范（Specs）作为系统行为的“单一事实来源”(Single Source of Truth) 。AI 的任何代码生成都必须严格基于并满足该规范。

### 2.2 独特的双工作区模型

为了精细控制变更，OpenSpec 在代码库中提倡物理分离事实（Truth）与提案（Proposals），通常包括：

- **`openspec/specs/`**: 存放经过验证并固化的当前系统规范。
- **`openspec/changes/`**: 存放正在提议的特性修改、需求 Draft（即 Spec Deltas）。
  这种结构化追踪方式能保持 Diffs 的显性与可审计性。

### 2.3 极致的 Token 效率

OpenSpec 采用“基于差异的上下文策略”（Diff-based context strategy）。面对巨大代码库，它通过仅向 AI 投喂当前的 "Spec Deltas" 和相关切片，而不是要求 AI 扫描整个代码仓库。这也极大加快了 AI 的响应速度和逻辑聚焦能力。

### 2.4 轻量级与高兼容性

与部分绑定特定 IDE 的方案不同，OpenSpec 框架轻量，不强制要求各种 API Keys。它天然融入各类现代 AI 开发工具，如：

- **Cursor**
- **Claude Code**
- **GitHub Copilot**
- **Amazon Q Developer**

## 3. 标准工作流 (Workflow)

要在项目里真正用好 OpenSpec，一般遵循以下步骤：

1. **构思与提案 (Propose)**
   - 不直接写代码，而是先在 `openspec/changes/` 创建一个关于核心功能或重构任务的提案规范（以结构化 Markdown 或 TypeScript 定义）。
2. **审查规范 (Review Spec)**
   - 团队/个人与 AI 首先针对这一份纯文本规范进行审查对齐，确认没有边界条件的遗漏或架构冲突。
3. **AI 实现 (Implement by Spec)**
   - 向 Cursor 或 Copilot 下达指令，让其完全依照 `openspec/changes/` 中的要求进行实际代码和测试用例的生成。支持借助平台原生的 Slash commands（例如配合特定的 Prompt 模板）。
4. **验证与合规检查 (Validate)**
   - OpenSpec 生态自带验证机制与测试断言。在 CI Pipeline 中运行，校验生成的代码是否 100% 覆盖了最初制定的执行规范。
5. **归档与固化 (Merge & Archive)**
   - 当任务完成，代码合入 Master 后，将临时变更 Draft 合并至 `openspec/specs/` 中，系统上下文就此更新。

## 4. 行业横向对比

| 框架/实践           | 定位与特点                                                                         | 优势与局限                                                                                                      |
| :------------------ | :--------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------- |
| **OpenSpec**        | 轻量级，规范驱动，核心围绕“提案与规范物理分离”来管理 AI Context。                  | **优势**：轻巧灵活，解耦具体模型与IDE；Token 成本极低。<br>**局限**：纯通过流程和文本约束，缺乏重型工具链加持。 |
| **GitHub Spec Kit** | GitHub 官方推出的重量级开源工具集，专注于通过 CLI 工具将 SDD 引入 Agentic Coding。 | **优势**：完整的脚手架支持、官方维护、开箱即用。<br>**局限**：相对较重，容易与既有架构产生冲突。                |
| **纯 Vibe Coding**  | 依靠开发者 Prompt 技术（如 Claude Artifacts 的即插即用）。                         | **优势**：无脑快捷，适合MVP构建。<br>**局限**：企业级的合规性、鲁棒性弱，无版本迭代的可追溯性。                 |

## 5. 最佳实践总结

1. **规范必须”可执行“**：撰写规范时应当具体到入参出参的数据结构、报错处理逻辑，而不要写空泛的描述。
2. **高优处理边界条件**：人类在撰写 Spec 时的核心职责是列出 Corner Cases，其余繁杂模板交由 AI 补全。
3. **CI/CD 自动化集成**：一定要利用其带来的可测性，将断言放到持续集成中，实现防呆和回归管控机制。
